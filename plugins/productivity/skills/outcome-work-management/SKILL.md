# Outcome Work Management

Turn an intention into a useful result, a practical next action, and evidence of what
actually happened. This is a candidate method to adapt and test, not a proven operating
standard. Use the user's language and existing workspace. Ordinary one-line tasks do
not need the whole framework.

## Read the situation before prescribing a process

Read the relevant goals, active plans, commitments and latest evidence already provided
or available in the authorized workspace. Distinguish current facts, old snapshots,
proposals and unknowns. Do not import one project's rules or private data into another.
Ask only for missing information that changes the decision; continue the useful parts.

If this method is being designed, deliver a draft and examples. Do not silently turn
examples into the user's actual OKRs, appointments, deadlines or financial records.
Reuse existing trackers and identifiers; do not create a second source of task truth.

## Choose how to reach the next decision

The hierarchy alone does not explain how a goal or result is produced. First identify
what is unresolved. Start at that point; an agreed goal or routine does not need a new
brainstorm. Apply the following methods selectively, in language appropriate to the area.

| Starting situation / question | Useful method and available specialist | Output to carry forward | Ready to move on when |
|---|---|---|---|
| Unclear need: what should change, for whom, and why now? | Examine current facts, stakeholder needs and constraints; distinguish symptoms from plausible causes. `synthesize-research` can synthesize existing interviews/feedback; it does not manufacture research. | Problem/opportunity statement with sources, consequences and unknowns | There is enough grounding to explore directions, or a specific evidence-gathering question |
| Need options: what could we pursue? | Brainstorm: frame, diverge, challenge, converge, capture. For product opportunities use `product-brainstorming`; select HMW, JTBD, analogy or another lens only if it helps. | Candidate directions, assumptions, alternatives set aside and cheap ways to test | Meaningfully different options and their critical unknowns are visible; ideas remain hypotheses |
| Need a goal: which change deserves commitment? | Compare value to the beneficiary, alignment, urgency, evidence, feasibility and opportunity cost; keep not-now/no-change as legitimate choices. Use `risk-assessment` if risk materially affects the choice. | Goal brief: proposed/selected O, why, supporting evidence, alternatives, scope, constraints, decision owner and review trigger | The choice is resolved within existing decision authority; otherwise retain a recommendation or bounded discovery step, not an invented commitment |
| Need KRs: what would establish success? | Define the observation or acceptance test first, inspect the baseline, choose a justified target and measurement source; distinguish outcome measures from delivery milestones. | KR definition with unit/condition, baseline or unknown, target rationale, period, owner, source and measurement cadence | The result is observable; missing baseline/target has an explicit measurement or decision step rather than a fabricated number |
| Need a way to achieve the goal: which intervention? | Compare approaches against the KR and assumptions; test the riskiest assumption where needed. Use `write-spec` for a product deliverable or `process-optimization` for a process change. | Chosen approach or experiment, scope, expected contribution, acceptance and unresolved dependencies | Evidence supports a bounded commitment, or the next work is explicitly an experiment |
| Need an executable plan: what fits this period? | Work backward from accepted outputs, expose dependencies and allocate actual capacity; use `sprint-planning` for team sprints, not automatically for personal days. | Period plan with linked work, intended outputs, capacity, dates and tradeoffs | The next work is actionable and overload or missing inputs are visible |
| Need reliable execution: how should this occurrence run? | Adapt the applicable work pattern or runbook to current inputs and risk. | Concrete checklist, output and verification record | Acceptance is met, or a failure/blocker and the next decision are recorded |
| Need to learn: did it help, and what changes next? | Compare baseline, actuals and acceptance; investigate causes rather than inferring them from correlation. Use `metrics-review` for available product metrics. | Continue/change/stop decision, evidence gaps, plan amendment or pattern revision | The conclusion matches the evidence and has a next action or explicit stopping point |

For a substantial item, make the selected procedure inspectable in a short note:
**Question → available inputs → method and why → expected output → acceptance/decision
condition → who or what uses that output next.** One sentence is enough for a small task.
If the method stops helping, change it with a reason; do not run all methods to fill a form.
When using a specialist, read its actual instructions if available. If it is absent,
use the lightweight method above and say what was done; do not claim the skill ran.

### Form a goal when none exists yet

Begin with the user's situation and intended benefit, not a made-up quarterly objective.
Separate "we observed this problem" from "we think this might be valuable". For example,
"build a local LLM" names a possible means; clarify who might benefit and which useful
change it could cause before promoting it to a goal. Personal learning can itself be
the intended benefit when that is the user's purpose.

Explore alternatives only as far as the decision needs. After brainstorming, capture
what emerged and perform the choice step separately; a compelling idea is not evidence
of demand, and a list of ideas is not an adopted O. Respect an ongoing exploratory
conversation: do not force commitment or produce a full quarterly plan prematurely.
If key facts are missing, the valid output can be a provisional direction plus a small
research/experiment brief: question, evidence needed, limit, and decision afterward.

Close with a compact goal brief when the user is ready to converge:
**Beneficiary/problem; desired change; evidence versus assumptions; options and tradeoffs;
recommended/selected direction and why; candidate KR or missing measurement; decision
status/owner; next action.** Reuse existing authority and settled choices. Ask only for
a consequential choice that is genuinely unresolved. A new objective needs no separate
approval ceremony when the user has already authorized the decision.

## Connect meaning, time and execution

These are relationships, not a mandatory folder tree:

| Object | Meaning | Minimum useful definition |
|---|---|---|
| Area | Continuing responsibility: company, finance, self, exploration | Purpose, owner, operating constraints |
| Objective | Desired change, usually within a quarter | Why it matters, period, accountable owner |
| Key Result | Observable result that demonstrates progress | Baseline if known, target or acceptance condition, due date, measurement source |
| Product/capability | Something maintained and used over time | User, problem, value hypothesis, current evidence of usefulness |
| Project | Bounded effort delivering a change | Output, acceptance, owner, dependencies, resource limit, linked KR or area |
| Work pattern | Reusable description of how a kind of work is handled | Purpose, trigger, inputs, default steps, output, acceptance |
| Plan | Intended allocation during a quarter/month/week/day | Linked work IDs, expected outputs, capacity, constraints |
| Work instance | A concrete occurrence of a pattern or one-off task | ID, parent link, date, owner, expected output, actual checklist and status |
| Evidence/review | What happened and what it means | Source, observation time, scope, result, uncertainty, next decision |

A KR may be a number, an operational condition, or an accepted milestone/project result.
If the company calls a project a KR, preserve that vocabulary and add its acceptance
condition; do not equate a project title or task completion rate with a business result.
Several projects may support one KR and one project may support several KRs. Keep one
canonical project ID with contribution links; never count the same result twice.
Necessary routines, wellbeing, obligations and exploration may link directly to an area.
Do not invent an OKR or a financial return to justify all of life.

## Plan at the right resolution

- **Quarter:** agree outcomes, the three monthly directions, constraints and how success
  will be recognized. Do not manufacture 90 daily checklists.
- **Month:** select deliverables and weekly intentions. Keep later months provisional.
- **Week:** choose achievable outputs around real availability and dependencies. Include
  recurring work and room for interruptions; propose capacity/WIP limits for local use,
  rather than enforcing an invented universal number.
- **Day:** select concrete work instances and create their child checklists from current
  facts. Carryovers retain their IDs and history. Do not regenerate them as new work.

Plans reference the same work records. Monthly/weekly/daily displays are views, not
copies to update independently. Use actual date ranges and the workspace timezone.
A week crossing a month boundary keeps one ID; each occurrence is counted on its actual
date, not twice in both months. A real deadline is distinct from a forecast date.
When capacity or dependencies change, reassess the forecast. If available evidence
cannot support a new date, retain the committed deadline but mark the forecast unknown
or at risk with the missing input; do not leave an unsupported on-time prediction.

Keep intended results distinguishable from measured actuals in the current document.
When expectations change, rewrite the current plan coherently with the relevant reason,
impact and next decision; retain an original commitment only where needed to assess it.
Do not create a revision diary or versioned document copies. Update mistaken summaries
from their sources without changing original measurements or misrepresenting lateness.

## Instantiate, execute and close

1. Pick the relevant current pattern, if one exists; adapt its steps to this occurrence.
   A new kind of work can start as a one-off. Repeated useful work may later become a pattern.
2. Name the output and acceptance before working. A small personal task can use the user's
   report; a technical, financial or customer claim needs evidence appropriate to that claim.
3. Record checklist steps, dependencies and the next action. Keep a task blocked when a
   required dependency is unavailable; identify who/what can unblock it.
4. Record what actually happened, including failed tests, interruption, time/cost if known,
   and the evidence link. A checked box is an execution record, not proof of an outcome.
5. Close at the strongest supported level. Separate task completion, output acceptance,
   and observed KR movement. Do not turn a test pass into a live-operation claim, a meeting
   into a sale, an invoice into received cash, or a projection into actual money.

Suggested instance states are planned, active, blocked, awaiting-verification, done,
cancelled. Map to the user's tracker instead of imposing a migration. Done requires the
defined acceptance; cancelled is not done. Missing information stays unknown, not zero.
Routine steps may use self-report without screenshots or ceremonial sign-offs. Record
skipped/not-applicable steps and a brief reason when that affects the acceptance claim.

## Handle incoming work and exploration

Capture spontaneous work with its reason and source. Triage it into: handle now, schedule,
delegate within existing authority, explore within a time/cost limit, or park/drop.
Urgent work can start with a minimal record and be completed afterward. If it displaces
planned work, record the tradeoff and update the forecast; do not conceal the displaced work.

An experiment needs a question, a bounded attempt, expected evidence, and a decision point:
continue, change approach, park or stop. A negative result that rules out an approach can
be an accepted output. Repetition without a new question or new evidence is a signal to
review the approach. A demonstration or interesting discovery is not proven market demand.
Track a value hypothesis separately: who benefits, what becomes better, how to test it,
and what would justify further investment. No invented revenue estimates are required.

Finance work references the existing ledger and evidence store. Plans and dashboards are
views over it, not a parallel ledger. Personal details stay in the private workspace.
This skill does not authorize payments, trades, messages, deployments or live actuations.
Use applicable existing authorization; ask only where a needed action lacks it.

## Review results and improve the method

At the cadence requested by the user, compare intended output with actual output,
acceptance and observed effect. Review blocked work, deadline risk, unplanned work,
capacity, and the next decision. Surface unknowns without inventing a progress percentage.
For a routine, adherence uses eligible occurrences, with missed/excluded occurrences
visible. For a KR, use its defined measure; do not average unrelated checklist percentages.
Show direct KR measurements independently; do not claim a project caused the change
without evidence of that contribution.

Rules have a source, purpose, scope and review trigger. Distinguish external obligations,
user-approved working agreements and experimental preferences. Adapt a template freely
within the task's authority; changing a binding obligation or accepted commitment requires
the relevant authority. Rewrite the current rule with its rationale and evaluation method.
Do not require a manual version ledger. Retain source identity in raw evidence only when
necessary for the project's reproducibility or acceptance, outside the ROOT summary.
If recordkeeping costs more than the decision it supports, simplify it. Improvement is
judged by useful outputs, clearer decisions and reduced rework, not document volume.

## Smallest useful artifact

Reuse the workspace's format. Prefer one current ROOT brief linking to the few key sources
and evidence. Operational agent records live under workspace/agents/<package>/<role>/,
outside ROOT's context. Rewrite the brief in place; if the structure changes materially,
recompose it fully and remove obsolete sections rather than append patches or v1/v2/final
documents. Keep reusable patterns separate from actual occurrences.
Use this compact shape for a work review or a plan, omitting irrelevant fields explicitly:

```markdown
# Work plan / review — [period, timezone]
Status: draft / adopted | Current as of: [date, source scope]

Purpose / area / O / KR: [existing links, or area + reason]
Desired result and measure: [baseline if known, target/acceptance, source]
Method: [open question -> chosen approach and why -> output -> decision condition]
Capacity and fixed commitments: [known constraints; unknowns marked]

| ID | Parent / current pattern | Expected output | Due / forecast | State | Actual / acceptance / evidence | Next action |
|---|---|---|---|---|---|---|

## Instance [existing ID] — [date]
Output / acceptance: [concrete result and how to recognize it]
- [ ] [Concrete step derived from current facts]
Actual: [observation or unknown; evidence and time]
Outcome: [observed effect, not inferred from checkbox count]

## Current decisions
Relevant adjustment and why; affected work/capacity; decision owner; unresolved choices.

## Review
Accepted outputs; evidence gaps; blockers; next decision; candidate process improvement.
```

Use existing specialist skills only when their actual deliverable is needed: PRD for a
product decision, sprint planning for a team allocation, a runbook for repeat operations.
No specialist skill, dashboard, automation, agent team or external connector is required
merely to plan a day. Creating a cadence does not schedule autonomous future runs.
